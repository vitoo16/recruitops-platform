# Private File Access Strategy

## Scope

RecruitOps uses the existing Supabase private bucket `recruitops-private` for candidate CVs and other sensitive recruitment documents.

The bucket is private and protected by Row Level Security (RLS) policies on `storage.objects`. Public object URLs are not part of the access model.

## Object key convention

Every ordinary recruiter-owned object must use the authenticated RecruitOps user ID as the first path segment:

```text
<user-uuid>/candidates/<candidate-or-application-id>/<filename>
```

Example:

```text
2f5646d5-4a8b-4514-859a-a9c5a1909890/candidates/candidate-123/cv.pdf
```

Do not place email addresses, phone numbers, candidate names or other PII in object paths.

## RLS access model

The migration `infra/supabase/migrations/20260927_private_storage_rls.sql` installs four policies for the `recruitops-private` bucket:

- authenticated `INSERT`;
- authenticated `SELECT`;
- authenticated `UPDATE`;
- authenticated `DELETE`.

For ordinary authenticated users, the first folder segment must equal `auth.uid()`.

Users with a trusted `app_metadata.recruitops_role` of `OWNER` or `ADMIN` may access objects across user prefixes for administrative/support workflows.

`raw_user_meta_data` / browser-editable metadata is not used for authorization.

## Download model

Private files must be downloaded using one of these controlled paths:

1. authenticated Supabase Storage download using the user's JWT, so RLS evaluates the caller; or
2. a short-lived signed URL generated only after the caller is authorized.

Never convert the bucket to public to simplify downloads.

Signed URLs should be short lived. A signed URL is itself a temporary bearer capability and must not be written to long-lived logs, analytics payloads or persistent public documents.

## Upload model

The upload path is generated by application code; do not trust a client-supplied arbitrary bucket path.

Before upload, application code must validate:

- authenticated caller;
- expected bucket;
- generated user-prefix path;
- maximum file size;
- allowed MIME type / extension;
- safe normalized filename;
- domain ownership/permission for the candidate or application.

The current RLS layer protects bucket/path authorization. MIME/file-size validation remains an application concern until explicit bucket restrictions are configured through a supported Storage API/provider setting.

## Deletion/update model

Ordinary users may update/delete only objects under their own user prefix. `OWNER` and `ADMIN` may perform cross-prefix administration.

Business-level deletion must later consider candidate retention policy and audit requirements before deleting an object.

## Service-role policy

A Supabase service-role/secret credential bypasses RLS and therefore must not be the default path for normal user file access.

If a future server-only maintenance job genuinely requires service-role access:

- use a server-only provider secret store;
- keep the scope of the job narrow;
- enforce authorization/business rules in RecruitOps before issuing file access;
- log the business action without logging the credential or signed URL;
- never expose the credential to the browser.

## Verification

The Supabase migration `private_storage_rls` has been applied to project `ybkmijhhhuqzatpnigsq` and the installed policies were queried back from `pg_policies`.

After the migration, Supabase Security Advisor reported no security lints.

## Future implementation tests

When Candidate/Application storage APIs are implemented, add integration tests that prove:

- unauthenticated upload/download is denied;
- recruiter A cannot access recruiter B's prefix;
- recruiter can access their own prefix;
- OWNER/ADMIN cross-prefix access works only with trusted app metadata;
- arbitrary client-supplied paths are rejected by the application;
- expired signed URLs no longer work;
- logs never contain JWTs, service-role credentials or signed URLs.
